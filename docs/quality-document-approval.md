# รหัสฉบับเอกสารและการตรวจสอบอนุมัติ

ปรับปรุง 26 ตุลาคม 2569

## รหัสเอกสาร

รหัสเอกสาร: `EDU-CUR-M.D.-SP-001`

ฉบับ: `000`

- `EDU-CUR-M.D.-SP-001` เป็นรหัสหลัก (`document_code`) คงเดิมตลอดอายุเอกสาร
- `001` ก่อนเลขฉบับเป็นลำดับเอกสาร แยกเอกสารคนละเรื่อง ระบบกำหนดเลขถัดไปอัตโนมัติเมื่อบันทึก เริ่ม 001 ภายในหน่วยงาน งาน หลักสูตร ระดับ และเกณฑ์เดียวกัน ผู้ใช้แก้เลขนี้ไม่ได้
- เลขฉบับแยกจากรหัสเอกสาร อนุมัติครั้งแรกเป็น `000` เมื่ออนุมัติการแก้ไขจึงเป็น `001`, `002` ตามลำดับ
- เอกสารระหว่างจัดทำและส่งตรวจแสดง **ฉบับร่าง / รออนุมัติ** ยังไม่มีเลขฉบับอนุมัติ ส่วนเลขที่เสนออนุมัติในรอบนั้นไม่ถือเป็นเลขฉบับที่มีผลใช้

ฉบับอนุมัติใหม่เริ่ม `000` สูงสุด `999` การส่งกลับแก้ไขและส่งตรวจซ้ำไม่เพิ่มเลขฉบับ เอกสารที่อนุมัติก่อนปรับระบบคงเลขเดิมไว้ ไม่เปลี่ยนเลขหรือแต่งข้อมูลอนุมัติย้อนหลัง

## ขั้นตอนใช้งาน

1. หน้าเพิ่มเอกสารแบ่งเป็น **จัดหมวดหมู่เอกสาร** และ **ชื่อและไฟล์เอกสาร** กด **บันทึกเอกสาร** ได้โดยตรง หรือเลือก **ตรวจสอบก่อนบันทึก** หากต้องการดูสรุป ระบบกำหนดลำดับแทน XXX และสร้างฉบับร่างที่ยังไม่กำหนดเลขฉบับอนุมัติ แนบไฟล์ภายหลังได้ หลังบันทึกกด **เปิดเอกสาร / ส่งตรวจ** ต่อได้ทันที
2. หรือเปิด **เอกสารคุณภาพทั้งหมด → กดชื่อเอกสาร / รายละเอียด** เจ้าของเอกสารหรือ admin แก้ชื่อ คำอธิบาย รายละเอียดการแก้ไข และแนบไฟล์ในแท็บ **เอกสาร**
3. ระบุ **สาระที่จัดทำหรือแก้ไข** และ **เหตุผลการจัดทำหรือแก้ไข** ทุกครั้ง รวมถึงครั้งแรก เช่น “จัดทำครั้งแรก” พร้อมเหตุผล กด **ส่งตรวจอนุมัติ** ได้เลย หากมีข้อมูลหรือไฟล์ที่ยังไม่บันทึก ปุ่มจะแสดง **บันทึกและส่งตรวจ** และบันทึกพร้อมส่งตรวจในครั้งเดียว ต้องมีไฟล์ PDF, Word หรือ Excel ไม่เกิน 20 MB ส่วน **บันทึกร่าง** ใช้เก็บงานไว้ทำต่อโดยยังไม่ส่งตรวจ
4. admin เปิด **การจัดเอกสารคุณภาพ → ตรวจสอบอนุมัติ** เลือกรายการ ตรวจสอบไฟล์และรายละเอียด
5. ตรวจข้อมูลและไฟล์แล้วกด **ทบทวนผ่าน** ระบบบันทึกผู้ทบทวนและเวลา จากนั้นระบุ **วันที่มีผลใช้บังคับ** และกด **อนุมัติฉบับ 000** พร้อมยืนยัน หรือ **ส่งกลับแก้ไข** พร้อมเหตุผล ผู้เป็นเจ้าของทะเบียน ผู้จัดทำล่าสุด หรือผู้ส่งตรวจทบทวนหรืออนุมัติฉบับของตนเองไม่ได้ ต้องใช้ admin คนละบัญชี ผู้ทบทวนและผู้อนุมัติเป็นคนเดียวกันได้ แต่เป็นการบันทึกคนละขั้นตอน
6. หลังอนุมัติ เอกสารได้รับเลขฉบับ เริ่มใช้งานเมื่อถึงวันที่มีผลใช้ เจ้าของหรือ admin กด **สร้างฉบับแก้ไข** เพื่อเริ่มรอบถัดไป โดยต้องแนบไฟล์ใหม่ หากมีฉบับอนุมัติที่ยังไม่ถึงวันมีผล ระบบให้รอฉบับนั้นมีผลก่อนสร้างร่างถัดไป

ระหว่างแก้ไข รออนุมัติ หรือรอวันมีผล ฉบับที่มีผลใช้เดิมยังใช้งานอยู่ เมื่อถึงวันที่มีผลตามเวลาไทย ระบบปรับฉบับปัจจุบันและสถานะฉบับเก่าในการอ่านหรือดำเนินการครั้งแรกของวันนั้น ไม่ต้องให้ผู้ใช้กดเปิดใช้เอง ไฟล์และข้อมูลอนุมัติเดิมแก้ทับไม่ได้ ฉบับเก่าที่ถูกแทนที่หรือยกเลิกใช้เปิดตรวจประวัติได้ตามสิทธิ์ แต่ดาวน์โหลดเพื่อใช้งานไม่ได้

## การแก้ทะเบียนและยกเลิกใช้

เปิดรายละเอียด → **ทะเบียนเอกสาร** เจ้าของหรือ admin เปลี่ยนตำแหน่งจัดเก็บได้โดยต้องระบุเหตุผล ระบบเก็บผู้แก้ เวลา และค่าก่อน/หลัง พร้อม Audit log โดยไม่เปลี่ยนเลขฉบับ ไฟล์ ผู้ทบทวน ผู้อนุมัติ วันอนุมัติ หรือวันที่มีผลใช้ การแก้เนื้อหา ชื่อเรื่อง หรือไฟล์ต้องทำผ่านฉบับร่างใหม่

admin กด **ยกเลิกใช้เอกสาร** และระบุเหตุผล ระบบปิดการใช้งานและเก็บทะเบียน ไฟล์ และประวัติไว้ แยกจากการลบเอกสารออกจากรายการใช้งาน ฉบับที่เคยถูกแทนที่ยังคงสถานะเดิม ส่วนฉบับอนุมัติที่ยังไม่ถูกแทนที่ รวมถึงที่รอวันมีผล จะเปลี่ยนเป็น “ยกเลิกใช้”

## ดาวน์โหลดเพื่อใช้งานและเปิดเพื่อตรวจทาน

- ปุ่ม **ดาวน์โหลด** ในหน้ารายการและ **ดาวน์โหลดฉบับอนุมัติ** ในรายละเอียดให้ไฟล์เฉพาะฉบับที่อนุมัติและมีผลใช้ปัจจุบัน ฉบับร่าง รออนุมัติ ส่งกลับแก้ไข รอวันมีผล ถูกแทนที่ และยกเลิกใช้ ไม่มีลิงก์ดาวน์โหลดเพื่อใช้งาน แม้เจ้าของหรือ admin เปิด URL ดาวน์โหลดโดยตรงก็ถูกปฏิเสธ
- ผู้จัดทำและผู้ตรวจ (เจ้าของทะเบียนและ admin) เปิดไฟล์ก่อนอนุมัติได้เฉพาะผ่าน **เปิดเพื่อตรวจทาน** พร้อมข้อความว่ายังไม่อนุมัติให้นำไปใช้งาน ใช้คำขอ `purpose=review` ที่ตรวจสิทธิ์จากฐานข้อมูลอีกครั้ง ผู้ใช้ทั่วไปและบัญชีปิดใช้งานเปิดไม่ได้ ชื่อไฟล์ที่ดาวน์โหลดตัดคำนำหน้า `สำหรับตรวจทาน-` และเลขสำเนาท้ายชื่อ เช่น ` (2)` ออก โดยคงชื่อเอกสารและนามสกุลเดิม เช่น `สำหรับตรวจทาน-เอกสาร (2).pdf` ดาวน์โหลดเป็น `เอกสาร.pdf`
- หากมีฉบับอนุมัติแล้วและกำลังแก้ไขฉบับถัดไป ปุ่มดาวน์โหลดในรายการยังให้ไฟล์ฉบับอนุมัติเดิม ส่วนร่างฉบับใหม่เปิดเพื่อตรวจทานได้ตามสิทธิ์
- สำเนารอบส่งตรวจที่ถูกส่งกลับยังเป็นไฟล์สำหรับตรวจทาน แม้รอบถัดมาของฉบับเดียวกันอนุมัติแล้ว ส่วนสำเนาของรอบที่อนุมัติและยังมีผลใช้ปัจจุบันใช้ดาวน์โหลดได้ตามสิทธิ์เดิมของเจ้าของและ admin ฉบับเก่าใช้เปิดอ้างอิงประวัติแทน
- ลิงก์ไฟล์เก่าที่เผยแพร่ตรงใน public ถูกปิด รวมถึง URL ที่เข้ารหัสชื่อโฟลเดอร์ ไฟล์เดิมยังอ่านได้ผ่าน endpoint ฉบับที่ตรวจสถานะและสิทธิ์ โดยไม่ย้ายหรือลบไฟล์ต้นฉบับ

## ติดตามเอกสารที่ส่งกลับแก้ไข

เปิด **การจัดเอกสารคุณภาพ → ติดตามการตรวจและแก้ไข** มีรายการแยกเป็น **ส่งกลับให้แก้ไข / ฉบับร่าง / รอตรวจอนุมัติ / อนุมัติแล้ว** พร้อมค้นหารหัส ชื่อเอกสาร หรือข้อเสนอแนะ เจ้าของเห็นเอกสารของตน ส่วน admin เห็นทุกทะเบียนที่ยังใช้งาน

1. เลือก **ส่งกลับให้แก้ไข → แก้ไขเอกสาร** หน้ารายละเอียดแสดงเหตุผล ผู้ตรวจ และเวลา ด้านข้างบนคอมพิวเตอร์ หรือก่อนช่องกรอกบนมือถือ ข้อความยาวกด **อ่านทั้งหมด** ได้
2. เปิด **ดูร่างที่ส่งกลับ** เพื่อตรวจเทียบกับต้นฉบับ หรือเลือก **รอบส่งตรวจ → เปิดสำเนาส่งตรวจ** เพื่อดูรอบก่อน
3. แก้ชื่อ คำอธิบาย หรือแนบไฟล์ใหม่ และระบุ **สิ่งที่แก้ไขตามข้อเสนอแนะ** ให้ตรงกับรอบนี้ หากยังไม่พร้อมส่ง กด **บันทึกร่าง** เพื่อเก็บงานไว้ทำต่อได้
4. กด **ส่งตรวจซ้ำ** ได้โดยไม่ต้องกดบันทึกร่างก่อน ระบบบันทึกการแก้ไขและส่งตรวจในครั้งเดียว ต้องมีคำอธิบายสิ่งที่แก้ไข และไม่รับการส่งซ้ำที่ข้อมูลและเนื้อหาไฟล์เหมือนรอบที่ถูกส่งกลับทุกอย่าง
5. ระหว่างรออนุมัติ ข้อมูลที่ส่งตรวจแก้ทับไม่ได้ ผู้ตรวจเห็นข้อเสนอแนะรอบก่อนคู่กับสิ่งที่ผู้จัดทำแก้ไข และเปิดสำเนาย้อนหลังได้แต่ละรอบ

สถานะ **ส่งกลับให้แก้ไข** คำนวณจากผลตรวจรอบล่าสุดของร่าง จึงยังใช้สถานะฐานข้อมูล `DRAFT` โดยไม่เพิ่ม enum หรือ migration รอบส่งตรวจเพิ่มเมื่อส่งซ้ำ ส่วนเลขฉบับอนุมัติยังเท่าเดิมจนกว่าจะอนุมัติสำเร็จ

## สำเนาของแต่ละรอบส่งตรวจ

ตั้งแต่ migration `20261024020000_preserve_quality_submission_drafts` ทุกครั้งที่ส่งตรวจจะเก็บชื่อเรื่อง คำอธิบาย รายละเอียดการแก้ไข ผู้ส่ง เวลา และสำเนาไฟล์แยกจากร่างที่แก้ไขได้ พร้อม SHA-256 ของไฟล์

- บันทึกร่างทั่วไปยังแก้ทับได้ ไม่สร้างสำเนาทุกครั้ง
- ส่งตรวจแล้วสร้างสำเนาใหม่ เช่น **สำเนาส่งตรวจ · เสนอฉบับ 000 · ส่งตรวจครั้งที่ 1**
- ส่งกลับแก้ไขจะบันทึกผู้ตรวจ เวลา และเหตุผลไว้กับรอบนั้น ข้อมูลและไฟล์ของสำเนาเดิมไม่ถูกแก้ทับ
- ส่งตรวจซ้ำสร้างรอบที่ 2, 3 ตามลำดับสำหรับ revision นั้น เมื่อเริ่มร่างของฉบับถัดไป รอบส่งตรวจเริ่มที่ 1 อีกครั้ง
- อนุมัติแล้วสำเนาส่งตรวจยังอยู่ และเชื่อมกับฉบับที่อนุมัติ เช่น 000 โดยฉบับอนุมัติใช้ไฟล์และข้อมูลจากสำเนาที่ตรวจจริง
- ก่อนอนุมัติและก่อนเปิดไฟล์สำเนา ระบบตรวจ hash หากไฟล์หายหรือเปลี่ยน จะไม่อนุมัติ/ให้รับไฟล์หลักฐานที่ไม่ตรงกัน ต้องคืนไฟล์ต้นฉบับหรือส่งกลับเพื่อแนบไฟล์และส่งตรวจใหม่

ดูที่ **เอกสารคุณภาพทั้งหมด → รายละเอียด → รอบส่งตรวจ → เปิดสำเนาส่งตรวจ** กด **กลับหน้ารายละเอียด** ที่ด้านบนหรือแถบด้านล่างเพื่อกลับไปฉบับและแท็บที่เปิดอยู่ก่อนหน้า โดยข้อมูลที่กำลังกรอกและไฟล์ที่เลือกไว้ยังอยู่ เจ้าของทะเบียนและ admin อ่านหลักฐานนี้ได้ ผู้ใช้ทั่วไปอ่านข้อมูลฉบับที่เคยอนุมัติและดาวน์โหลดได้เฉพาะฉบับปัจจุบัน เอกสารที่ลบจากรายการใช้งานยังเก็บสำเนาไว้ให้ admin ตรวจสอบ

## หน้าจอและปุ่มหลัก

- หน้ารายการแสดงข้อมูลหลัก 4 คอลัมน์ ดาวน์โหลดฉบับอนุมัติได้ทันที กด **ตัวกรอง** เมื่อต้องการกรองเพิ่มเติม หรือกดเครื่องหมายบวกเพื่ออ่านหมวดหมู่และวันที่สร้าง บนมือถือแสดงเป็นรายการการ์ดเพื่อไม่ต้องเลื่อนแนวนอน
- หน้ารายละเอียดแยกเป็น **เอกสาร / รอบส่งตรวจ / ประวัติการทำงาน / ทะเบียนเอกสาร** ประวัติไม่ได้แสดงต่อท้ายแบบฟอร์ม ปุ่มดาวน์โหลดฉบับอนุมัติหรือเปิดเพื่อตรวจทานอยู่ที่หัวหน้าต่างตามสถานะและสิทธิ์ ปุ่มบันทึก ส่งตรวจ ทบทวน อนุมัติ และส่งกลับ อยู่ในแถบด้านล่างเสมอ เนื้อหายาวเลื่อนภายในพื้นที่เนื้อหาเดียว
- การเลือกฉบับใช้เฉพาะฉบับเอกสาร สำเนา 000 ของแต่ละรอบอยู่ในแท็บ **รอบส่งตรวจ** เพื่อแยกการทำงานปัจจุบันออกจากการอ่านหลักฐานย้อนหลัง
- **บันทึกร่าง** เป็นทางเลือกสำหรับงานที่ยังไม่พร้อมส่ง ปุ่ม **ส่งตรวจอนุมัติ / บันทึกและส่งตรวจ / ส่งตรวจซ้ำ** บันทึกข้อมูลและไฟล์ล่าสุด พร้อมสร้างสำเนาส่งตรวจใน transaction เดียว หากตรวจสอบไม่ผ่านจะไม่บันทึกบางส่วนหรือสร้างรอบส่งตรวจค้างไว้ และข้อมูลที่กรอกบนหน้าจอยังอยู่
- **เก็บไว้กรอกต่อ** เก็บข้อมูลฟอร์มในเครื่อง ยังไม่สร้างเอกสารในระบบและไม่เก็บไฟล์แนบ ส่วน **บันทึกเอกสาร** สร้างทะเบียนในฐานข้อมูล

สำหรับข้อมูลก่อนเปิดใช้: ย้ายเฉพาะ payload ของเอกสารที่กำลังรออนุมัติ ซึ่งยังคงทราบข้อมูลแน่นอน โดยระบุ `LEGACY_PENDING` และเวลาเก็บสำเนาจริงแยกจากเวลาส่งเดิม ไม่สร้างสำเนาย้อนหลังของรอบที่ส่งกลับหรืออนุมัติไปแล้ว หากเดิมไม่ได้เก็บข้อมูลนั้นไว้

## สิทธิ์และข้อมูล

admin ลบเอกสารออกจากรายการใช้งานได้จากหน้า **ลบเอกสารคุณภาพ** โดยเก็บไฟล์และประวัติเดิมไว้ มีประวัติรวมทั้งระบบที่ **Audit log** ดู [คู่มือการลบและ Audit log](./audit-log-and-deletion.md)

- ผู้เข้าสู่ระบบที่บัญชียังเปิดใช้งานอ่านฉบับที่อนุมัติแล้วได้ทุกหน่วยงาน
- เจ้าของทะเบียนและ admin อ่านร่างหรือฉบับรออนุมัติได้ เจ้าของหรือ admin แก้ร่างและส่งตรวจได้
- ตรวจบทบาทและสถานะบัญชีจากฐานข้อมูลทุกคำขอ ไม่อาศัยการซ่อนปุ่มเพียงอย่างเดียว
- ประวัติบันทึกการสร้าง แก้ไข ส่งตรวจ ส่งกลับ และอนุมัติ พร้อมบัญชีผู้ดำเนินการ ความเห็น และเวลา
- มีร่างหรือฉบับรออนุมัติได้หนึ่งรายการต่อทะเบียน ใช้ UNIQUE ของ `(document_id, open_slot)` โดยฉบับเปิดใช้ `open_slot = 1` และฉบับอนุมัติใช้ NULL
- `lock_version` ป้องกันคำขอจากหน้าจอที่ข้อมูลเก่า การเปลี่ยนสถานะและเพิ่มเลขฉบับล็อกทะเบียนใน transaction แบบ Read Committed เพื่อป้องกันอนุมัติหรือเพิ่มเลขซ้ำเมื่อมีคำขอพร้อมกัน
- การสร้างทะเบียนล็อกหน่วยงานใน transaction แบบ Read Committed ก่อนหาลำดับสูงสุดและเพิ่มหนึ่ง จึงรองรับการสร้างกลุ่มแรกและการบันทึกพร้อมกัน ไม่รับลำดับจาก browser รักษาเลขเดิมไว้และปฏิเสธการสร้างเมื่อกลุ่มนั้นถึง 999
- ไฟล์ใหม่เก็บใน `storage/qa-documents` ซึ่งไม่เผยแพร่ตรงผ่าน public และดาวน์โหลดผ่าน `/api/quality-documents/revisions/[id]/file` ที่ตรวจสถานะอนุมัติและสิทธิ์ ส่วนไฟล์เก่าใน `public/uploads/qa-documents` ยังอยู่ที่เดิมแต่ URL ตรงถูกปิด ต้องเปิดผ่าน endpoint ฉบับเช่นกัน
- เก็บไฟล์ที่เคยบันทึกไว้เพื่อการกู้คืน จึงต้องสำรองทั้งฐานข้อมูล `storage/qa-documents` และ `public/uploads` และเผื่อพื้นที่สำหรับไฟล์ร่างที่ถูกแทนที่

## ติดตั้งและทดสอบ

### บันทึกร่างแล้วขึ้น “เชื่อมต่อไม่สำเร็จ” เมื่อแนบไฟล์เกิน 10 MB

Next.js Proxy มีขีดจำกัดการเก็บ request body แยกจาก Server Actions หากเพิ่มเฉพาะ `serverActions.bodySizeLimit` แต่ยังใช้ Proxy ค่าเริ่มต้น 10 MB ไฟล์ multipart ที่ใหญ่กว่านั้นจะถูกตัดและเกิด `Unexpected end of form` ก่อนเข้าโค้ดบันทึก

`next.config.ts` กำหนด `experimental.proxyClientMaxBodySize` และ `experimental.serverActions.bodySizeLimit` เป็น 25 MB เท่ากัน เพื่อรับไฟล์ขนาดสูงสุด 20 MiB พร้อมข้อมูลฟอร์ม กฎขนาดไฟล์ของแอปยังคง 20 MiB ฝั่ง browser ปฏิเสธไฟล์เกินขนาดทันที และฝั่ง server ตรวจซ้ำ ไม่ต้องแก้ฐานข้อมูล เมื่อแก้ config ต้องให้ dev server restart หรือ build และเปิด production server ใหม่

ทดสอบผ่าน HTTP จริงหลังเปิด `npm run dev` โดยใช้ทะเบียนและบัญชีทดสอบชั่วคราว:

```powershell
$env:RUN_HTTP_TESTS = '1'
node --test --test-isolation=none tests/quality-document-upload.http.test.mjs
node --test --test-isolation=none tests/quality-document-download.http.test.mjs
Remove-Item Env:RUN_HTTP_TESTS
```

ครอบคลุมบันทึกโดยไม่แนบไฟล์ ไฟล์ 11 MiB ไฟล์ 20 MiB ตรวจ SHA-256 ว่าไม่ถูกตัด ปฏิเสธไฟล์เกิน 20 MiB โดยไม่แก้ร่างเดิม แก้ข้อมูลโดยคงไฟล์แนบเดิมไว้ และบันทึกพร้อมส่งตรวจในคำขอเดียวด้วยไฟล์ 20 MiB

การทดสอบดาวน์โหลดตรวจคำขอ HTTP จริงสำหรับฉบับร่าง รออนุมัติ ส่งกลับแก้ไข และอนุมัติแล้ว ครอบคลุมเจ้าของ ผู้ตรวจ ผู้ใช้ทั่วไป บัญชีปิดใช้งาน และคำขอที่ไม่ได้เข้าสู่ระบบ ตรวจลิงก์ในรายการและรายละเอียด รวมถึงการปิด URL public เก่าและการคงไฟล์อนุมัติเดิมขณะมีร่างฉบับใหม่

### Migration และการทดสอบ workflow

ระดับระเบียบปฏิบัติ (SP) ไม่ต้องเลือกเกณฑ์ประเมิน รหัสเอกสารจึงข้ามส่วนเกณฑ์ เช่น `MGT-M.D.-SP-001` และแสดงฉบับแยกต่างหาก ระดับอื่นยังต้องเลือกเกณฑ์ตามหลักสูตร ระบบล้างเกณฑ์เดิมเมื่อเปลี่ยนเป็น SP หรือเปิดร่าง SP ที่เก็บในเบราว์เซอร์ และไม่ใช้เกณฑ์ที่ส่งค้างมากับคำขอบันทึก SP

Migration `20261026000000_allow_sp_without_criterion` อนุญาตให้ `criterion_id` ว่างได้ โดยคงข้อมูลและรหัสเอกสารเดิมไว้

Migration `20261026010000_document_control_54` แยกกรณียังไม่อนุมัติด้วย NULL เพื่อให้เลข 0 เป็นฉบับแรกที่อนุมัติได้ เพิ่มเหตุผล ผู้ทบทวน วันมีผลใช้รายฉบับ ประวัติแก้ทะเบียน และสถานะถูกแทนที่/ยกเลิกใช้ คงเลขฉบับที่เคยอนุมัติไว้ทั้งหมด ไม่เปลี่ยน 001 เดิมเป็น 000 และไม่เติมข้อมูลทบทวน เหตุผล หรือวันมีผลของฉบับเก่าที่ไม่มีหลักฐาน ข้อมูลเก่าแสดงว่ายังไม่มีข้อมูล กรณีรออนุมัติเก่าที่ข้อมูลบังคับไม่ครบ ต้องส่งกลับให้ผู้จัดทำเติมข้อมูลและส่งตรวจใหม่

Migration `20261024000000_add_quality_document_approval` เพิ่มข้อมูลฉบับและ `docs_qa_review_events` ย้ายทะเบียน DRAFT เดิมเป็นร่าง `000` โดยเก็บรหัสหลัก ชื่อ และไฟล์เดิมไว้ ฉบับเก่าที่อนุมัติแล้วเก็บ label เดิมและเริ่มตัวนับที่ 1 ประวัติเดิมที่ไม่ทราบผู้อนุมัติจะไม่สร้างชื่อหรือเวลาอนุมัติย้อนหลัง

หากเปิด `npm run dev` อยู่ ให้หยุดด้วย Ctrl+C ก่อน migrate/generate และเปิดใหม่หลัง generate เสร็จ Prisma Client ที่โหลดอยู่ใน process เดิมอาจยังเป็น schema เก่าแม้หน้าเว็บจะ refresh แล้ว อาการที่พบได้คือโหลดรายการไม่สำเร็จ และ server แจ้ง `Unknown argument open_slot` การ refresh เบราว์เซอร์อย่างเดียวไม่เปลี่ยน Client ใน process เดิม

หลังเปลี่ยนเกณฑ์ให้ว่างได้ หาก SP ยังบันทึกไม่สำเร็จและ server แจ้ง `Argument criterion_id is missing` ให้รีสตาร์ต dev server หลัง generate เช่นกัน ทดสอบคำขอบันทึกจริงหลังเปิด server ใหม่ได้ด้วย `$env:RUN_HTTP_TESTS = '1'` แล้วรัน `node --test --test-isolation=none tests/quality-document-create.http.test.mjs` ซึ่งตรวจทั้ง SP แบบมีไฟล์แนบ ไม่มีไฟล์แนบ และการโหลดรายการที่ไม่มีเกณฑ์

```powershell
node node_modules/prisma/build/index.js migrate deploy
node node_modules/prisma/build/index.js generate
node prisma/materialize-submission-files.mjs
$env:RUN_DB_TESTS = '1'
node --test --test-isolation=none tests/quality-document-workflow.integration.test.mjs
node node_modules/typescript/bin/tsc --noEmit --incremental false
node node_modules/next/dist/bin/next build
```

Integration test สร้างข้อมูลแยกด้วยรหัสเฉพาะและล้างใน `finally` ครอบคลุมสิทธิ์ การส่งกลับ การอนุมัติพร้อมกัน ฉบับถัดไป และการเก็บไฟล์ฉบับเดิม

สคริปต์ `materialize-submission-files.mjs` ทำสำเนาไฟล์และ hash สำหรับรายการรออนุมัติที่นำเข้า รันซ้ำได้โดยข้ามรายการที่ทำเสร็จ หากไฟล์ต้นทางหายจะรายงาน ID ที่ทำไม่ได้และไม่สร้างหลักฐานปลอม ให้คืนไฟล์เดิมแล้วรันซ้ำ หรือส่งกลับเพื่อให้เจ้าของแนบไฟล์ใหม่
